## Session 2026-08-21 (afternoon) -- Silent Step-2 failure root-caused and fixed (two independent bugs); automated-run status added to the dashboard (Drew, Kevin's explicit go-ahead to proceed on all three without checking back first)

**Scope:** The 08:30 scheduled run fired on schedule; Step 1 (`fetch_osm_report.py`) succeeded (log shows the real attachment found and saved); Step 2 never started -- no error in the log, nothing in Windows event logs. Kevin gave three explicit instructions: (1) root-cause and fix the silent failure, with finer-grained diagnostics so a future failure pinpoints the exact line/step; (2) add a real "did this morning's automated run happen and did it work" indicator to the dashboard itself, distinct from the existing manual-update timestamp; (3) manually run the real pipeline now against today's already-fetched attachment to catch the dashboard up. Pre-authorized to proceed on all three without checking back.

**Root cause 1 -- confirmed via live bisection, not guesswork:** `Task Scheduler`'s own operational log showed the task completing in 10 seconds with return code `2147942655` (`0x800700FF`), and reproducing the run visibly (not hidden) showed cmd.exe's own parser error directly: `- was unexpected at this time.` Bisecting the real script line-by-line (safe scratch copies, real preamble + progressively more of the real body) isolated it to the failure-branch echo inside `if not "%FETCH_EXIT%"=="0" ( ... )`:
```
echo [%RUN_TS%] Step 1/2 FAILED (exit %FETCH_EXIT%) - Step 2 SKIPPED. ...
```
cmd.exe's block parser ends a parenthesized `if`/`for` block at the **first** unescaped `)` it meets while scanning -- it does not balance against an earlier `(` in the same text -- so the `)` immediately after `%FETCH_EXIT%` was read as the block's real close. Everything the script intended to run after that point (the rest of that line, the remaining body lines, and the block's real closing `)`) was misparsed as stray top-level tokens, starting with the literal text ` - Step 2 SKIPPED...`, whose leading `-` produces cmd's classic `- was unexpected at this time.` -- written only to the console, which is always invisible since this runs fully hidden via `wscript.exe` windowStyle 0. That is exactly why nothing appeared in the log or in Windows event logs: this happens at cmd's own parse layer, before any of the script's own log-append statements are ever reached. **This fired on every run regardless of Step 1's real outcome** -- cmd.exe must fully parse an if-block to know where to resume even when the condition is false and the block is being skipped, which is exactly what happened this morning (Step 1 genuinely succeeded; the block should never have been entered at all, yet the script still died parsing it). Confirmed the fix (reword the message to avoid literal parens entirely, rather than relying on remembering to `^(`/`^)`-escape) resolves it via the same bisection method before touching the real files.

**Root cause 2 -- a second, independent bug found only once root cause 1 was fixed:** re-running the (now bug-1-fixed) script for real got past Step 1 and into Step 2, then failed cleanly with `'"Update HRIS Dashboard.bat"' is not recognized as an internal or external command`. Isolated this directly (safe dummy `.bat` files, not the real `Update HRIS Dashboard.bat`, to avoid triggering real `pip install`/GitHub pushes/hanging `pause` prompts during testing): **this machine's `cmd.exe` cannot launch a second `.bat`/`.cmd` FILE from a `cmd.exe` process that is itself already executing a batch file** -- confirmed via `call "x.bat"`, bare `x.bat`, and a freshly spawned `cmd /c "x.bat"` all failing identically, with `Test-Path`/`dir`/`where` all confirming the target file genuinely exists in the correct working directory. Confirmed this is specific to **script-file** targets, not a blanket "cmd can't spawn cmd": nested `cmd /c dir`, `cmd /c echo`, and even double-nested `cmd /c "cmd /c echo"` all worked fine from the exact same nested context, and curl.exe/python.exe (real `.exe` targets) already worked fine live in Step 1. Confirmed the fix empirically before applying it live: routing the invocation through PowerShell as an intermediary succeeds every time from the same nested context --
```
powershell -NoProfile -Command "Get-Content 'empty_stdin.txt' | & '.\Update HRIS Dashboard.bat'; exit $LASTEXITCODE"
```
-- tested against a real dummy containing a genuine `pause` first, confirming it doesn't hang (the piped empty file gives `pause` an immediate EOF, same job `< NUL` used to do for the old, now-broken-here `call` invocation) and that the real exit code propagates correctly, before applying it to the real file.

**Finer-grained diagnostics, per Kevin's explicit ask:** the whole run now executes as `call :main > "%LOG_FILE%" 2>&1` -- one redirection covering the entire subroutine, both stdout *and* stderr -- instead of the old scattered per-line `>> %LOG_FILE%` appends. This means **any future cmd.exe parser error, not just this specific one, lands in the log file automatically**, because the redirection applies to everything that happens during that call, including cmd's own error output. Before this change, a script-level syntax error was structurally invisible no matter how much per-line logging existed, since execution never reached any of those log-append statements once cmd's parser choked -- which is exactly what happened this morning. Also: all three `curl` downloads (`fetch_osm_report.py`, `Update HRIS Dashboard.bat`, `push_automation_status.py`) now use `-f` (`--fail`), so an HTTP error (404/5xx) returns a real nonzero exit code instead of silently saving the error page's body as if it were the file -- this actually bit during testing (`push_automation_status.py` 404'd because it hadn't been pushed to `main` yet; without `-f`, curl saved the literal 14-byte string `404: Not Found` as the "script", which python then failed on with a confusing `SyntaxError` instead of a clear download-failed message).

**New -- dashboard automated-run status indicator (Kevin's ask #2):** `push_automation_status.py` (new file, repo root) pushes `data/last_automated_run.json` to GitHub via the same `GITHUB_PAT` + Contents-API pattern already used by `import_osm_report.py`, called by `Run_HRIS_Auto_Refresh.bat` at **every** exit point -- success and every distinct failure mode (fetch-script-download-failed, fetch-failed, update-bat-download-failed, dashboard-update-failed) -- so it's the automation's own self-reported record of what happened on its last attempt, independent of whether `tickets.json` itself changed. `index.html` now shows a badge -- **"Last automated refresh: `<time>` — Success/Failed"** -- next to the existing manual-update subtitle line, styled with the same green/red palette already established for status pills and Linda insight cards (`HANDOVER.md`'s own "Colour System" section, unchanged). Sourced from this new JSON file via a `loadAutomationStatus()` function mirroring the existing `loadData()` fetch pattern exactly; falls back to a neutral grey "No automated run recorded yet" state if the file doesn't exist (e.g. before this feature's first run) rather than erroring. This directly addresses Kevin's core complaint: a failed automated run leaving yesterday's `tickets.json` in place would otherwise look identical to a fresh successful run, since the old subtitle only ever reflected whoever last successfully finished the *manual* pipeline's own timestamp.
